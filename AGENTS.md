## Development

When starting the dev server, use background mode:

```
astro dev --background
```

Manage the background server with `astro dev stop`, `astro dev status`, and `astro dev logs`.

## Updating shrine pages for SEO (structured data, meta descriptions, FAQ)

Follow this procedure when adding SEO improvements to shrine pages, rather than editing pages ad hoc.

**Standing rule: every newly added shrine gets this treatment before/alongside its own commit** — don't let new shrines accumulate as a backlog. Structured data and meta descriptions are automatic (template-driven, see step 2), but the `faq:` frontmatter array (step 4-5) must be added by hand for each new shrine, in both `src/content/shrines/*.md` and `src/content/shrines-en/*.md`.

For the pre-existing backlog of older shrines that predate this process, work through them by the `order` frontmatter field, oldest first, in batches (10 at a time has worked well) — see the shrine-portal-seo-improvements memory for current progress.

1. **Prioritize by actual traffic when triaging a backlog.** Check GA4 for which shrine pages get real visits before spending effort — don't touch all pages uniformly. Start with the highest-traffic ones. (Not needed for new shrines — those get FAQ immediately regardless of traffic.)
2. **Put site-wide logic in the template, not in individual Markdown files.** Meta descriptions and JSON-LD structured data are generated by [src/lib/seo.ts](src/lib/seo.ts) and called from `src/pages/shrines/[id].astro` / `src/pages/en/shrines/[id].astro`. One code change applies to every shrine, including future additions — never hardcode per-shrine SEO text in a page template.
3. **Generate meta descriptions from existing frontmatter** (deities, benefits, founded date) rather than reusing one generic sentence across all pages — duplicate meta descriptions hurt CTR. Because frontmatter fields are free text and vary a lot in length/format between shrines, always truncate safely to a max length rather than assuming a field is short.
4. **Base FAQ content only on facts already present in that shrine's frontmatter and body** (hours, goshuin fee/hours, access, parking, one distinctive fact from the body). Never invent details. Phrase questions the way someone would actually search (e.g. "〇〇神社 御朱印 時間", "〇〇神社 駐車場"). When writing both `src/content/shrines/*.md` and `src/content/shrines-en/*.md` for the same shrine, read both frontmatters first so JA/EN facts stay consistent.
5. **FAQ display and `FAQPage` JSON-LD also live in the template**, driven by a `faq: [{question, answer}]` array in the Markdown frontmatter (see `src/content.config.ts`) — Markdown files hold only data, not markup or schema.
6. **Always verify with a real build**, not just a read-through: run `npm run build` and inspect the generated HTML for the actual `<meta name="description">` and `<script type="application/ld+json">` output before considering the change done.
7. **Commit in meaningful units** (e.g. "SEO structured data + meta descriptions" separate from "shrine FAQs") rather than one big mixed commit.
8. **After deploying, request re-indexing** for changed URLs via Search Console's URL Inspection tool ("インデックス登録をリクエスト") to speed up Google picking up the change. Note Search Console enforces a daily quota on these requests (roughly ~10-12/day) — expect to spread a large batch across multiple days.

## Related-shrines links (engagement/exit-rate feature)

Every shrine page automatically shows a "関連する神社" (Related Shrines) block linking to a few other shrines that share the same `prefecture` and/or `benefits` tags — see [src/lib/related.ts](src/lib/related.ts) and [src/components/RelatedShrines.astro](src/components/RelatedShrines.astro), wired into all six `src/pages/{,en/,zh/,es/,fr/,ko/}shrines/[id].astro` templates. This is fully automatic: it only reads `prefecture` and `benefits`, which every shrine already has, so newly added shrines (including ones authored outside this repo/session) get related links with zero extra work — never add manual "related shrine IDs" to frontmatter for this.

## Scheduled publishing ("予約投稿") — available, but NOT the default

**Default policy (decided by the user, 2026-10-08): publish all 6 languages of a shrine on the SAME day** — give every language file the same `publishDate` (today). The user does not want users to hit missing/404 language pages. Only stagger languages if the user explicitly asks again.

The mechanism below exists and is tested, but is currently unused (no Vercel deploy hook / GitHub secret has been set up):

A shrine/guide entry is only built once its frontmatter `publishDate` has arrived (Japan time) — see [src/lib/content.ts](src/lib/content.ts). All 6 language files are written together; each language file carries its own `publishDate`, so if staggering were wanted, ja/zh could go live today, en a week later, etc. Nothing else changes in how shrines are authored.

- Every page/query must go through `getPublished()` / `getPublishedEntry()` from `src/lib/content.ts`, never raw `getCollection()` / `getEntry()` (that would publish future-dated entries immediately).
- `hreflang` tags (Layout.astro) and the language switcher only list languages that are live for a given shrine/guide page.
- The site is static, so a release needs a rebuild on/after the date. `.github/workflows/scheduled-release.yml` runs daily at 00:05 JST and, only if `node scripts/release-schedule.mjs --due` says something is due, POSTs the `VERCEL_DEPLOY_HOOK_URL` secret (Vercel deploy hook). Any normal push also rebuilds.
- `node scripts/release-schedule.mjs` prints the upcoming-release schedule grouped by date, shrine and language (report it to the user after adding shrines).
- Test an "as of" date: `PUBLISH_AS_OF=2026-10-01 npm run build` (use `2099-01-01` to include everything).
- Don't mix this up with `src/data/updates.ts` (the homepage feed): add a shrine to the feed only when its ja page goes live; the feed already skips slugs that aren't live in the current locale.
